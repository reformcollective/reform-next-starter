## 1. Plain-language explainer

- Bunny.net is a CDN company (a network of servers that hands out files fast). Bunny Stream is its video product, bolted onto that CDN.
- You make a Video Library (a project bucket with settings: which resolutions to make, security, player look, which storage regions). A library has a numeric Library ID and a pull zone hostname like `vz-cc3ec516-c62.b-cdn.net`.
- You get a video in by dashboard upload, HTTP API (create a video, PUT the file), resumable TUS upload (good for browsers), or "fetch from URL" (you give Bunny a URL and it downloads it). Source: docs/stream/index, url-fetch, tus-resumable-uploads.
- Every video gets a GUID (e.g. `6dae38a5-9322-401a-a6e6-76e7cbb368dd`). Library ID + Video GUID identify it everywhere: API calls, embed URLs, CDN paths.
- A Collection is only a folder inside one library for organising videos. Docs: "not public", "do not function as playlists", cannot generate a public URL for a collection. It is irrelevant to playback.
- Bunny then transcodes the upload into several resolutions (we observed 240p to 1080p) and packages them as HLS (a playlist file that points at small chunk files; the player switches quality as bandwidth changes). Optional MP4 copies ("MP4 fallback") are made only if enabled before upload.
- It also makes thumbnails, an animated preview, and a sprite sheet of seek-bar thumbnails.
- Delivery has three shapes: (a) Bunny's own player in an iframe (`player.mediadelivery.net/embed/{library}/{guid}`), (b) a direct HLS URL you give to your own player, (c) a direct MP4 URL.
- Why a team picks it: cheap, pay-for-use pricing, free standard encoding, a free hosted player, a simple API. Why not: less polish and ecosystem than Mux (fewer SDKs, a thin Sanity story, a player that is only controllable through an iframe postMessage protocol).
- Pricing model (official pricing pages, bunny.net/pricing/stream/ and docs/stream/pricing): standard encoding and the player are free; you pay for storage and CDN bandwidth; paid add-ons exist (Premium Encoding, AI transcription, Enterprise DRM); $1 monthly minimum; 14-day free trial button on the page. Rates are on those pages, not repeated here.

## 3. DISCREPANCIES (docs vs observed)

1. oEmbed field names: OpenAPI schema `VideoOEmbedModel` says `thumbnailUrl` (camelCase), `providerName`, `providerUrl`. The live JSON uses `thumbnail_url`, `provider_name`, `provider_url` (standard oEmbed snake_case) and adds `thumbnail_width`/`thumbnail_height` not in the schema. Trust the live JSON.
2. Pull zone hostname: docs and task brief show `vz-<id>`; the real host is `vz-cc3ec516-c62.b-cdn.net`, not derived from the library ID `767357`. The host must be read from the API (`videoPlaylistUrl`) or the library settings, it cannot be computed.
3. player.js upstream: README lists `seeked` event and `on/off/supports`, but the shipped `dist/player-0.1.0.js` has no `seeked`; the progress payload is `{percent}` in README, `{seconds,duration}` in SPEC.rst, and `{percent,seconds,duration}` in Bunny docs.
4. player.js README says hosted at `//cdn.embed.ly/player-0.1.0.min.js`; Bunny hosts a different, extended build at `assets.mediadelivery.net/playerjs/playerjs-latest.min.js` with playback-rate methods and `seeked`/`playbackratechange`. Bunny docs confirm this in a NOTE; the npm package gets none of it (confirmed by grep).
5. Marketing vs docs pricing: bunny.net/pricing/stream/ says "all security features completely free" and "No security fees"; docs/stream/pricing lists MediaCage Enterprise DRM at a $99/month per-library base fee plus per-license fees (Basic DRM is free). Not strictly contradictory (Enterprise needs sales) but the marketing line overstates.
6. Marketing pricing page says "Free encoding", docs say standard encoding is free but Premium Encoding is per-minute billed; also "Free encoding is a shared service intended for low volume workloads" (docs encoding.md).
7. Docs say embed autoplay defaults to `true`; this is a library-setting default (docs: "Where the default is a library setting, the parameter overrides that setting"), so the true default is per library. Not observed.
8. Referrer behavior: docs describe domain allow-listing via the iframe Referer. Observed: the demo library's CDN files (playlist, segments, mp4, thumbnail) return 403 when no `Referer` is sent but accept arbitrary referrers (`example.org`, `example.com`), while the embed page accepts no Referer. So that library has referer-required but not domain-restricted behavior; this is a per-library setting and the demo may differ from a customer library.
9. Docs token page says CDN token auth "uses the same key" as embed tokens; CDN docs describe Basic (MD5, deprecated) and Advanced (HMAC-SHA256) schemes while the embed token is SHA256 of key + video_id + expires. The hashing and path inputs differ per layer. Not live-tested (needs a key).
10. Docs (embedding.md) describe `preload` default true and `disableIosPlayer` etc.; the embed HTML observed uses `autoplay playsinline preload="auto"` on the element, consistent but not proof of param handling.

## 4. Verdict inputs (facts only)

Can Bunny be played as a plain HLS source (no iframe)? Yes. Observed on the public demo: standard HLS master + variants, CORS `*`, range support, H.264/AAC, 6 s TS segments. Needs hls.js on non-Safari (Safari plays it natively). Requirements/caveats observed or documented:

- The page must send a `Referer` (observed 403 without) and, if the library has Allowed domains, be on the list.
- Library must not have MediaCage DRM on (Basic DRM disables direct file access and third-party players; Enterprise DRM needs a third-party player integration with licence URLs).
- Token-protected libraries need CDN directory tokens for HLS (embed tokens do not apply); tokens must be signed server-side.
- MP4 `play_*p.mp4` exists only if enabled pre-upload.

What would be lost by going iframe-less (vs the Bunny player):

- Captions: VTT files exist at `captions/{lang}.vtt` but are NOT in the HLS master (observed no SUBTITLES lines), so the UniversalVideo component must attach `<track>` itself and learn the language list from the API or its own CMS data. Live caption fetch NOT VERIFIED.
- Alternate audio tracks: present as `EXT-X-MEDIA TYPE=AUDIO` in HLS (observed), so hls.js/Safari can expose them.
- Analytics: Bunny's view/watch-time stats and heatmaps are fed by the Bunny player (observed `track-session` call in its HTML; docs say each playback session feeds statistics). With a plain element they would not be sent (inference); CDN bandwidth stats still come from the pull zone (inference, not tested).
- DRM: Basic MediaCage is incompatible with direct playback by design; Enterprise needs Widevine/FairPlay licence wiring (Shaka/Bitmovin guides exist).
- Chapters/moments, VAST ads, Chromecast/AirPlay UI, heatmap, remember-position: part of Bunny's player, not of the files.
- Seek-bar thumbnails: sprite sheets are a fixed convention (A11), usable but self-assembled.

Estimated adapter surface if wrapping the iframe via player.js (UniversalVideo as a custom element implementing HTMLMediaElement):

- Mappable directly: play, pause, paused, muted (mute/unmute/getMuted), volume (0-100 scaled to 0-1), duration, currentTime (get/set), loop, playbackRate (Bunny build only; npm build needs `send`) = about 9 properties/methods (17 protocol methods incl. add/removeEventListener).
- Mappable events: ready, play, pause, ended, timeupdate, progress, seeked, playbackratechange, error = 9. Missing for a full media-elements contract: `loadedmetadata`, `canplay`, `playing`, `waiting`, `seeking`, `durationchange`, `volumechange`, `ratechange` mapping, `readyState`, `buffered`, `seekable`, `videoWidth/videoHeight`, `error` object detail, `src` as a Bunny `libraryId/guid`, `poster`, `controls`, text tracks, quality levels, fullscreen/PiP (iframe handles internally). All of these would be fabricated, stubbed or unavailable. Also: everything async (getters use callbacks), iframe plus `ready` timing hazards under SSR (C9), one-iframe-per-src routing rule (C6), and an extra script load.
- Plain-HLS route: the surface is the real `<video>` element, so the adapter is mostly a thin `src` resolver (library, guid, pull zone host to playlist URL, thumbnail, optional mp4) plus hls.js, plus the referrer/token work. Mux's media-elements already include an hls-video element, so an HLS-source adapter is comparatively small. (Statement about Mux elements not verified in this research, from the task framing only.)
- Sanity: only one Bunny plugin exists (F1), Studio 6 only, third party, with the API key in the browser unless a proxy is run; Mux has a Sanity-maintained plugin for Studio 5 and 6.
