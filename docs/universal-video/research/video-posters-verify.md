# Video poster / thumbnail verification (2026-10-27)

Labels: VERIFIED = literally on a primary page I fetched. NOT VERIFIED = not found on a primary page. "Observed" = my own live HTTP request, not documentation.
Note: WebFetch summarises pages with a small model, so quotes marked "(summary)" are the tool's paraphrase/quote; Vimeo and Twitch were read from raw page source/JS and are literal.

## 1. YouTube

- VERIFIED: `snippet.thumbnails` keys and sizes for videos: default 120x90, medium 320x180, high 480x360, standard 640x480, maxres 1280x720. https://developers.google.com/youtube/v3/docs/videos and https://developers.google.com/youtube/v3/docs/thumbnails (the thumbnails page also lists channel sizes).
- VERIFIED: maxres is NOT guaranteed. Thumbnails page says standard "is available for some videos and other resources that refer to videos" and maxres "This image size is available for some videos and other resources that refer to videos" (summary). Also "an HD video may support higher resolution thumbnails than non-HD videos."
- VERIFIED: `videos.list` costs 1 quota unit: https://developers.google.com/youtube/v3/docs/videos/list
- VERIFIED: API key rule: "A request that does not provide an OAuth 2.0 token must send an API key." https://developers.google.com/youtube/registering_an_application (page does not name videos.list; applying the rule to public videos.list is my inference).
- NOT VERIFIED: that `img.youtube.com/vi/<id>/<name>.jpg` (or `i.ytimg.com`) is documented by YouTube. Searches of developers.google.com / support.google.com returned only third-party pages. The Data API pages above never mention the `/vi/<id>/` URL pattern or the names mqdefault/hqdefault/sddefault/maxresdefault. Treat that pattern as undocumented by YouTube.
- NOT VERIFIED: any official YouTube page documenting the `https://www.youtube.com/oembed` endpoint, its `thumbnail_url` size, key requirement, or behavior for private/unlisted/embedding-disabled videos. The oEmbed spec page (https://oembed.com/) only shows `https://www.youtube.com/oembed` inside an example and defines `thumbnail_url`/`thumbnail_width`/`thumbnail_height` ("A URL to a thumbnail image representing the resource"; the three must appear together).
- Observed only (not documentation): `GET https://www.youtube.com/oembed?url=https://www.youtube.com/watch?v=dQw4w9WgXcQ&format=json` returned 200 with no key, `thumbnail_url` = `https://i.ytimg.com/vi/dQw4w9WgXcQ/hqdefault.jpg`, thumbnail 480x360. A nonexistent id returned HTTP 400. `https://img.youtube.com/vi/<id>/maxresdefault.jpg` returned an image for both a real id and a fake id (a placeholder image, so a 200 does not prove a real maxres exists). Private/unlisted/embed-disabled behavior was not tested.

## 2. Vimeo

Source: https://developer.vimeo.com/api/oembed/videos (read from the page's JS bundle, literal).

- VERIFIED: endpoint `https://vimeo.com/api/oembed.json?url=<url-encoded video URL>&width=480&height=360`.
- VERIFIED: sample response includes `thumbnail_url` ("https://i.vimeocdn.com/video/721904228_295x166"), `thumbnail_width` 295, `thumbnail_height` 221, `thumbnail_url_with_play_button` (an `i.vimeocdn.com/filter/overlay?...crawler_play.png` URL). Note the sample's 295x166 URL vs height 221 is as published.
- VERIFIED: other request params listed include `width`, `height`, `maxwidth`, `thumbnail_id` ("The ID of the thumbnail to load from the video's available thumbnail set" , this is a player/embed option table entry).
- NOT VERIFIED: that `width` changes the returned thumbnail size. The page shows width/height for the embed iframe; the page text I read does not say they resize the thumbnail.
- VERIFIED: unlisted: "be sure to send the entire URL, not just the portion with the video ID. The URL of an unlisted video contains an additional string of characters that you must include with your GET request"; and when privacy is Unlisted "you must use the URL, and the URL must include the `h` parameter."
- VERIFIED: domain-level privacy (`whitelist`): oEmbed returns "a simplified response containing no private metadata" (sample has `html`, `width`, `height`, `domain_status_code: 403`, `video_id`, `uri` and NO thumbnail fields). Full response requires sending a `Referer` header set to the permitted domain (`curl -e http://example.com ...`). Implication: a server-side lookup would need that Referer.
- VERIFIED: "If you've (very) recently updated the video... it might take a couple minutes before the oEmbed response reflects those changes."
- NOT VERIFIED: access token requirement for oEmbed (the page lists none in the parts I read; a third-party blog says none needed, not primary).
- NOT VERIFIED: oEmbed-specific rate limit. Vimeo help center https://help.vimeo.com/hc/en-us/articles/12427783954065-Rate-limits (search snippet only, page not fetched) says limits are per minute, 429 on excess, and specific figures are "on the Developer Site"; I did not find an oEmbed number.

## 3. Wistia, Twitch, TikTok, Spotify

- Wistia: https://docs.wistia.com/docs/wistia-and-oembed . VERIFIED: endpoint `https://fast.wistia.com/oembed` (JSON; `/oembed.xml` for XML), required `url`, optional `format`, `callback`, `maxwidth`, `maxheight`, `width`, `height`. Response includes `thumbnail_url`, `thumbnail_width`, `thumbnail_height` ("This URL is a direct link to the thumbnail image asset"; no Wistia play button overlay by default). Domain restrictions: oEmbed "still resolves and returns the embed code normally"; restriction enforced at render. Locked `/s/` share links return an empty response. Errors 404 (bad URL or media failed processing), 501 (no embed code, incl. still processing). NOT VERIFIED: auth and rate limits (page documents neither). Resize params like `image_crop_resized`/`image_resize`: only seen in sample URLs and a third-party blog; NOT VERIFIED as documented.
- Twitch: https://dev.twitch.tv/docs/api/reference/ (raw page read). VERIFIED: Get Videos (`GET https://api.twitch.tv/helix/videos`) "Requires an app access token or user access token"; its `thumbnail_url`: "Before using the URL, you must replace the %{width} and %{height} placeholders... Due to current limitations, ${width} must be 320 and ${height} must be 180." Get Streams also requires an app or user token; its `thumbnail_url` is "an image of a frame from the last 5 minutes of the stream" with `{width}x{height}` placeholders to fill in. Get Clips `thumbnail_url`: "A URL to a thumbnail image of the clip" (example `...-preview-480x272.jpg`). Embed docs https://dev.twitch.tv/docs/embed/video-and-clips/ do not mention thumbnails/posters/oEmbed; they say embeds must be at least 400x300 and mobile cannot autoplay without interaction. NOT VERIFIED: that Twitch has an official oEmbed endpoint (none found). Helix rate limit number not read (page points to a Rate Limits guide).
- TikTok: https://developers.tiktok.com/doc/embed-videos . VERIFIED: `GET https://www.tiktok.com/oembed?url=<video link>`; documented example response fields: `version, type, width, height, html, provider_url, provider_name, embed_product_id, embed_type`. The page does NOT list `thumbnail_url`/`thumbnail_width`; auth and rate limits not mentioned. Page says Embed Videos "will be deprecated soon" and recommends Embed Player for new integrations (summary). A third-party Go client suggests a thumbnail_url exists in practice: NOT VERIFIED officially.
- Spotify: https://developer.spotify.com/documentation/embeds/reference/oembed . VERIFIED: `GET https://open.spotify.com/oembed` (base `https://open.spotify.com` or `https://spotify.link`), required `url` (podcast show, episode, artist, album or track). Response fields: `html, width, height, version, provider_name, provider_url, type ("rich"), title, thumbnail_url ("URL of a thumbnail image for the item", string, nullable), thumbnail_width, thumbnail_height` (nullable; example 300x300). Auth and rate limits not specified on the page. A Spotify Community thread (https://community.spotify.com/t5/Spotify-for-Developers/Missing-thumbnail-urls-for-album-artist-and-track/td-p/6538050) reports missing thumbnails for some types (search snippet only; not a primary statement).

## 4. YouTube policy on facades

- Required Minimum Functionality https://developers.google.com/youtube/terms/required-minimum-functionality (summary quotes): "Any YouTube thumbnail that initiates a playback must be at least 120 pixels wide and 70 pixels tall." "Embedded players must have a viewport that is at least 200px by 200px." Autoplay: players "should initiate playback immediately when the page loads" but must not start until the player is visible (more than half visible). Count: "A page or screen must not have more than one YouTube player that automatically plays content simultaneously." Overlays: you "must not display overlays, frames, or other visual elements in front of any part of a YouTube embedded player" or use them "to obscure any part of an embedded player, including player controls." Also "must not make changes to the YouTube player that are not explicitly described by the API documentation." The page does NOT address a custom poster/play-button facade or deferring the iframe until click (VERIFIED absence per the fetch summary).
- Developer Policies Guide https://developers.google.com/youtube/terms/developer-policies-guide : "In general, video metadata such as thumbnail and title must be visible to the viewer and unmodified." "The video thumbnail must not be altered." "Custom play buttons over the YouTube thumbnail are acceptable, but tapping must initiate playback." Overlays "for the purposes of obtaining user consent or playback controls" acceptable if they do not conflict with player UI. Page does not address autoplay, multiple players, or storing thumbnails. (Quotes via fetch summary; re-read the page before relying on exact wording.) Implication stated by the page: a custom play button over the YouTube thumbnail is acceptable; an uploaded override image replacing the thumbnail is NOT addressed and may conflict with "must not be altered" (my reading, not stated).
- Developer Policies https://developers.google.com/youtube/terms/developer-policies : autoplay sharing clause (III.E.4.i): autoplay means data sharing "will therefore occur upon page load"; setting Autoplay to false limits data shared before interaction. No explicit multiple-player rule found there.
- IFrame API reference https://developers.google.com/youtube/iframe_api_reference : `cueVideoById` "loads the specified video's thumbnail and prepares the player"; "The player does not request the video until" playVideo/seekTo is called (summary). Page does not mention lazy loading, multiple players, or oEmbed.

## 5. Where lookups can run

- (a) Sanity webhooks https://www.sanity.io/docs/webhooks : VERIFIED webhooks are "automated HTTP requests" to a URL you set; fire on created/updated/deleted; by default only when changes are published (unpublish counts as delete). Document Actions https://www.sanity.io/docs/studio/document-actions : VERIFIED you can replace the `publish` action in `document.actions`, wrap the original, run code in `onHandle`, then call `originalResult.onHandle()`. NOT VERIFIED: any official statement that these are suited to fetching thumbnails or patching the document back (a webhook receiver patching the document is not on the pages I read).
- (b) Next 16.4.3 docs in `node_modules/next/dist/docs/01-app/` (non-cacheComponents path, `02-guides/caching-without-cache-components.md` and `03-api-reference/04-functions/fetch.md`). Literal: "By default, `fetch` requests are not cached. You can cache individual requests by setting the `cache` option to `'force-cache'`." Fetch API ref: default `auto no cache`: "fetches the resource from the remote server on every request in development, but will fetch once during `next build` because the route will be statically prerendered. If Request-time APIs are detected on the route, Next.js will fetch the resource on every request." `force-cache`: looks up the server-side cache keyed on URL, method, headers, body; "Only responses with a `200` HTTP status code are stored." `next.revalidate`: `false` caches indefinitely, `0` prevents caching, a number is a lifetime in seconds. `next.tags` enables `revalidateTag`. Guide line 111: "A `fetch` request that sets no `cache` option is fetched once during `next build` if it is reachable before any Request-time APIs are used... Requests discovered after a Request-time API run on every request." GET fetches with same URL/options are memoized within one render pass. Route `revalidate`: a lower per-fetch `revalidate` decreases the whole route's interval. Draft Mode bypasses the cache entirely.
- (c) Client-side: NOT VERIFIED from provider docs that browser CORS is permitted for any of these oEmbed endpoints (I did not test or find CORS statements). Twitch Get Videos/Streams need a token, which cannot be exposed safely client-side (inference). Vimeo domain-privacy lookups depend on a `Referer` header.

## 6. Licensing / ToS on storing or re-hosting thumbnails

- YouTube Developer Policies https://developers.google.com/youtube/terms/developer-policies (summary): authorized API data may be stored "for no longer than 30 calendar days"; after that "must either delete or refresh the stored data"; prohibits downloading/caching/storing "copies of YouTube audiovisual content"; attribution: make clear YouTube is the source of content including thumbnails. The page has no explicit rule on re-hosting thumbnails (VERIFIED absence per summary); whether a thumbnail counts as "audiovisual content" is NOT VERIFIED. API Terms https://developers.google.com/youtube/terms/api-services-terms-of-service : "no rights or licenses are granted to reproduce or distribute audiovisual content" (s.16.3, summary). The 30-day clause did not appear in the Terms page, only in the Developer Policies.
- Vimeo: NOT VERIFIED (no thumbnail storage/re-hosting clause found; Vimeo best practices recommend caching metadata per search snippet of help.vimeo.com, not read in full).
- Wistia, Twitch, TikTok, Spotify: NOT VERIFIED (I did not read their ToS/developer policy pages for thumbnail storage).
